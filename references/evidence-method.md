# 取证与分析协议

## 1. 证据盘点

先建清单，不立即下结论。编号从 `E01` 起连续递增；截图、代码、日志、页面共用这一序列。

| 证据编号 | 类型 | 来源/位置 | 覆盖范围 | 时间/版本 | 可访问性 | 可支持的问题 | 局限 |
|---|---|---|---|---|---|---|---|
| E01 | | | | | | | |

证据优先级通常为：可复现运行结果与代码路径 > 连续操作记录 > 完整截图 > 单张截图 > 用户转述 > 宣传资料。运行时状态与代码设计仍可能不同，需交叉验证。

## 2. 证据就绪度

逐项检查：产品对象、目标用户与核心任务、主流程起点/确认/执行/结果、修改/回退、失败/中断、关键页面/按钮/状态/资产/错误；技术结论所需的代码/接口/日志；模型结论所需的模型/Agent/检索/生成证据；数据结论所需的对象/字段/状态/引用。

给出：`可完整执行 / 仅可局部执行 / 不可执行`。

- 不可执行：没有一手证据或证据与目标无关。停止实质拆解并索取材料。
- 仅可局部执行：有证据但不能覆盖完整流程或某层。限定范围，只做能追溯的部分。
- 可完整执行：证据覆盖指定范围的正常、修改和异常路径，并足以支撑相关层级。

## 3. 取证顺序

交互产品从最早记录开始检查：初始输入/上传/默认值；第一次反馈；每个确认门；确认前后页面、状态和资产变化；修改、返回、撤销、重试和中断；错误、余额、权限、安全或网络问题；最终资产、预览、编辑、导出/发布入口；聊天、工作区、任务、资产库和历史版本对账。

代码产品补充检查入口、模块依赖、API、状态模型、任务执行、存储对象、错误路径和测试；不得仅凭目录名断言运行行为。

## 4. 结论等级

| 等级 | 条件 | 写法 |
|---|---|---|
| 页面/代码事实 | 可直接看到或定位 | 只说看到什么 |
| 合理推断 | 多条事实或一条强证据支持 | 写推导链与替代解释 |
| 尚未确认 | 缺关键证据或存在冲突 | 写所需补证 |
| 产品建议 | 目标设计或改进 | 与现状分区 |

## 5. 完成声明交叉验证

对“完成、成功、已保存、已发布”至少寻找一个独立结果：页面状态、真实可预览资产、任务结果/日志、数据或上下文字段、外部系统状态、用户确认记录。

冲突编号从 `C01` 起：

| 冲突编号 | 来源 A | 来源 B | 可确认事实 | 影响 | 当前处理 | 待补证据 |
|---|---|---|---|---|---|---|
| C01 | | | | | | |

## 6. 四层联结

用核心对象贯穿四层，不输出四个孤立章节：

| 链路步骤 | 用户层 | 技术层 | 模型层 | 数据层 | 输入状态 | 输出状态 | 证据 |
|---|---|---|---|---|---|---|---|

说明用户动作触发什么事件、技术模块如何处理、是否调用模型/工具、读写什么数据、成功/失败/中断产生什么状态、下游如何消费。证据列只填写 `E01` 这类编号。

## 7. 图形要求

至少包含：含正常/修改/失败中断的用户流程图；四层跨层流程或架构图；核心数据生产者—消费者或实体关系图。异步状态明显时增加状态机图。判断节点用菱形或视觉等价表示，分支写条件，每个关键节点引用证据编号，推断节点使用不同样式。使用 HTML 模板中的 SVG/HTML 结构，不要输出 Mermaid 代码块。

## 8. 停止条件

- 用户指定范围已覆盖且 HTML 已校验；
- 证据不足且已列出最小补充材料；
- 需要登录、验证码、付费、生成、发布、删除等新授权；
- 继续探索将越出指定产品、账号、项目或安全边界。
